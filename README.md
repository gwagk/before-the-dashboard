# กว่าจะเป็น Dashboard
## จากปัญหาสู่ข้อมูล จากข้อมูลสู่การตัดสินใจ

**Before the Dashboard: From Problems to Evidence-Based Decisions**  
**Knowledge Management (KM) | ฉบับเริ่มต้น 1.0 | 8 ตุลาคม 2569**

> Dashboard ไม่ใช่จุดเริ่มต้นของงาน แต่เป็นผลลัพธ์ของกระบวนการคิด กำหนดคำถาม จัดการข้อมูล ตรวจสอบหลักฐาน และออกแบบการตัดสินใจ

**ชื่อ Repository ที่เสนอ:** `before-the-dashboard`  
**ขอบเขต:** คู่มือเชิงวิชาการและปฏิบัติสำหรับงานกำกับติดตามภาครัฐและองค์กร โดยไม่ยึดติดกับซอฟต์แวร์  
**หลักการ:** Data Before Dashboard · Evidence Before Visualization · Decision Before Decoration

---

## บทคัดย่อ

ความล้มเหลวของ Dashboard มักไม่เกิดจากการเลือกชนิดกราฟผิดเพียงอย่างเดียว แต่เริ่มตั้งแต่ไม่มีโจทย์การตัดสินใจ ขาดนิยามตัวชี้วัด ข้อมูลต้นทางไม่ตรงกัน ไม่แยกข้อเท็จจริงออกจากข้อสันนิษฐาน และไม่มีผู้รับผิดชอบการแก้ไขปัญหาที่ตรวจพบ ตำรานี้นำเสนอกระบวนการ 12 ขั้นตอน พร้อมหลักฐานที่ต้องมีและเกณฑ์ผ่านแต่ละขั้น (*stage gates*) เพื่อให้ Dashboard เป็นเครื่องมือกำกับติดตามที่เชื่อถือได้ ไม่ใช่เพียงภาพสวยงาม

## วัตถุประสงค์การเรียนรู้

เมื่อศึกษาและปฏิบัติตาม ผู้เรียนควรสามารถ (1) แปลงปัญหาเป็นคำถามเชิงบริหาร (2) กำหนดขอบเขตและตัวชี้วัดอย่างตรวจสอบย้อนกลับได้ (3) ประเมินคุณภาพข้อมูลและความเสี่ยงในการตีความ (4) ออกแบบ Dashboard ขั้นต่ำที่ช่วยตัดสินใจ และ (5) วางระบบทบทวนและจัดการความรู้ต่อเนื่อง

## กรอบแนวคิดทางวิชาการ

- **Systems Thinking:** มองกระบวนการตั้งแต่แหล่งข้อมูล ผู้ปฏิบัติ ผู้ตัดสินใจ ไปจนถึงผลการดำเนินงาน; ระวังการแก้เพียงอาการปลายทาง
- **PDCA:** Plan—นิยามปัญหาและตัวชี้วัด; Do—จัดเก็บ/ตรวจข้อมูล; Check—ประเมินความถูกต้องและผลลัพธ์; Act—ปรับปรุงกระบวนการ
- **Lean:** ตัดขั้นตอน การเก็บข้อมูล และภาพแสดงผลที่ไม่ก่อประโยชน์ต่อการตัดสินใจ
- **Data Quality:** ประเมินความถูกต้อง (accuracy), ความครบถ้วน (completeness), ความสอดคล้อง (consistency), ความทันเวลา (timeliness), ความไม่ซ้ำซ้อน (uniqueness) และความสมเหตุสมผล (validity)
- **Data Governance / Least Privilege:** กำหนดเจ้าของข้อมูล สิทธิ์เข้าถึง แหล่งอ้างอิง และประวัติการเปลี่ยนแปลง
- **Decision Support:** ตัวชี้วัดทุกตัวต้องสัมพันธ์กับคำถาม ผู้รับผิดชอบ และการดำเนินการที่เป็นไปได้

กรอบข้างต้นเป็นการประยุกต์แนวคิดวิชาการทั่วไปให้เป็นขั้นตอนปฏิบัติของคู่มือนี้ มิใช่การอ้างว่ามีมาตรฐานสากลฉบับเดียวกำหนด 12 ขั้นตอนตามลำดับนี้

# ส่วนที่ 1 — 12 ขั้นตอนก่อนจะเป็น Dashboard

### ขั้นที่ 1 ระบุปัญหา (Problem Identification)
**คำถาม:** ปัญหาเกิดอะไรขึ้น ใครได้รับผลกระทบ และเหตุใดต้องติดตาม?  
**ลงมือทำ:** เขียนปัญหา 1–3 ประโยค แยกอาการออกจากสาเหตุและความเชื่อ  
**ผลผลิต:** Problem statement + ผู้รับผิดชอบโจทย์  
**เกณฑ์ผ่าน:** อธิบายได้ว่าหากไม่แก้จะเกิดผลกระทบอะไร

### ขั้นที่ 2 ระบุการตัดสินใจ (Decision Definition)
**คำถาม:** ใครจะใช้ข้อมูลตัดสินใจอะไร เมื่อไร และทำอะไรได้จริง?  
**ลงมือทำ:** ทำตาราง *คำถาม → ผู้ตัดสินใจ → ทางเลือกการดำเนินการ → รอบเวลา*  
**ผลผลิต:** Decision map  
**เกณฑ์ผ่าน:** ทุกคำถามสำคัญเชื่อมโยงกับการกระทำได้; หากดูแล้วทำอะไรไม่ได้ ให้ทบทวนความจำเป็น

### ขั้นที่ 3 กำหนดขอบเขตและหน่วยนับ (Scope & Unit of Analysis)
**คำถาม:** นับใคร/อะไร รวมและยกเว้นกรณีใด ช่วงเวลาใด?  
**ลงมือทำ:** นิยามประชากรเป้าหมาย หน่วยนับ เงื่อนไขเข้า–ออก และกรณีพิเศษ  
**ผลผลิต:** Scope statement + inclusion/exclusion rules  
**เกณฑ์ผ่าน:** ผู้ตรวจสอบสองคนใช้กติกาเดียวกันแล้วได้จำนวนตรงกัน

### ขั้นที่ 4 สำรวจแหล่งข้อมูล (Data Source Inventory)
**คำถาม:** ข้อมูลมาจากไหน ใครดูแล อัปเดตเมื่อไร เชื่อถือได้ระดับใด?  
**ลงมือทำ:** ลงทะเบียนชื่อชุดข้อมูล ผู้ดูแล ฟิลด์สำคัญ ความถี่ วันที่อ้างอิง ข้อจำกัด  
**ผลผลิต:** Data inventory / source register  
**เกณฑ์ผ่าน:** ตัวเลขสำคัญย้อนกลับไปหาแหล่งข้อมูลได้

### ขั้นที่ 5 กำหนดนิยามข้อมูลและตัวชี้วัด (Data Dictionary & KPI Specification)
**คำถาม:** คำว่า “ติดตั้งสำเร็จ”, “ออนไลน์”, “ครอบคลุม” ต่างกันอย่างไร?  
**ลงมือทำ:** ระบุสูตร ตัวตั้ง ตัวหาร หน่วย เวลา แหล่งข้อมูล และข้อยกเว้น  
**ผลผลิต:** KPI dictionary  
**เกณฑ์ผ่าน:** คำนวณซ้ำได้และไม่มีคำที่ตีความได้สองแบบ

### ขั้นที่ 6 ตรวจคุณภาพข้อมูล (Data Quality Assessment)
**คำถาม:** ข้อมูลซ้ำ ขาด เก่า ผิดรูปแบบ หรือขัดกันหรือไม่?  
**ลงมือทำ:** ตรวจ missing, duplicates, invalid values, stale records, outliers และความสอดคล้องข้ามชุด  
**ผลผลิต:** Quality report + issue log  
**เกณฑ์ผ่าน:** ทราบข้อบกพร่องที่อาจทำให้สรุปผลผิด พร้อมผู้รับผิดชอบตรวจแก้

### ขั้นที่ 7 เชื่อมโยงและกระทบยอด (Matching & Reconciliation)
**คำถาม:** รายการสองระบบเป็นสิ่งเดียวกันจริงหรือไม่?  
**ลงมือทำ:** ใช้รหัสอ้างอิงที่เสถียรก่อน; ถ้าใช้ชื่อ ต้องกำหนดกติกา normalize และบันทึกกรณีไม่ตรงกัน  
**ผลผลิต:** Matched / Source A only / Source B only / Ambiguous  
**เกณฑ์ผ่าน:** ไม่บังคับจับคู่ด้วยการเดา; มีรายการรอตรวจสอบชัดเจน

### ขั้นที่ 8 ประเมินความเสี่ยงและกำกับข้อมูล (Risk & Governance)
**คำถาม:** ข้อมูลใดเปิดเผยได้ ใครควรเห็น และความผิดพลาดจะส่งผลอย่างไร?  
**ลงมือทำ:** ประเมินความเสี่ยงด้านการตีความ ความเป็นส่วนตัว ความมั่นคงปลอดภัย และการเปลี่ยนแปลงข้อมูล  
**ผลผลิต:** Access matrix + data handling rules  
**เกณฑ์ผ่าน:** ผู้ชมรายงานเห็นเฉพาะข้อมูลที่จำเป็น; การแชร์สิทธิ์ไม่เปิดเผยข้อมูลดิบโดยไม่ตั้งใจ

### ขั้นที่ 9 ออกแบบสารสนเทศสำหรับการตัดสินใจ (Information Design)
**คำถาม:** ผู้ใช้ต้องเห็นอะไรภายใน 30 วินาที?  
**ลงมือทำ:** จัดลำดับ *ภาพรวม → ข้อยกเว้น → แนวโน้ม/ความคืบหน้า → สิ่งที่ต้องทำ*  
**ผลผลิต:** Dashboard sketch / wireframe  
**เกณฑ์ผ่าน:** อธิบายประเด็นสำคัญได้โดยไม่ต้องสอนอ่านกราฟนาน

### ขั้นที่ 10 สร้าง Minimum Viable Monitoring (MVM)
**คำถาม:** อะไรคือหน้าจอขั้นต่ำที่ใช้งานจริงได้?  
**ลงมือทำ:** เริ่มจากตาราง KPI, วันเวลาอ้างอิง, กราฟเท่าที่จำเป็น, ข้อยกเว้น และเจ้าของงาน  
**ผลผลิต:** Dashboard รุ่นแรก  
**เกณฑ์ผ่าน:** ใช้กำกับติดตามและระบุงานถัดไปได้; ยังไม่จำเป็นต้องมี Web App หรือข้อมูลสด

### ขั้นที่ 11 ทดสอบและรับรองผล (Verification & Validation)
**คำถาม:** ตัวเลขถูกหรือไม่ และแสดงความหมายตรงกับสิ่งที่ผู้ใช้เข้าใจหรือไม่?  
**ลงมือทำ:** ตรวจตัวตั้ง/ตัวหารกับข้อมูลต้นทาง; ทดสอบ edge cases; ให้ผู้ใช้จริงอธิบายสิ่งที่เห็น  
**ผลผลิต:** Test checklist + sign-off  
**เกณฑ์ผ่าน:** ไม่มีการใช้ตัวเลขหนึ่งไปอ้างผลอีกเรื่องหนึ่ง เช่น name match ≠ online

### ขั้นที่ 12 ใช้งาน ติดตาม และเก็บ KM (Operate, Review & Learn)
**คำถาม:** ใครอัปเดต เมื่อไร ตรวจอะไร และเมื่อใดควรหยุดเพิ่มฟังก์ชัน?  
**ลงมือทำ:** กำหนดรอบอัปเดต owner, exception follow-up, change log, retrospective และเกณฑ์ปรับปรุง  
**ผลผลิต:** Operating SOP + KM record  
**เกณฑ์ผ่าน:** คนอื่นรับช่วงงานได้โดยไม่ต้องเริ่มค้นหาความหมายข้อมูลใหม่

**บทเรียน:** แดชบอร์ดที่มีเพียง 4–6 ตัวเลขอาจมีคุณค่ามากกว่าระบบใหญ่ หากแต่ละตัวเลขมีนิยามชัด ตรวจย้อนกลับได้ และเชื่อมกับการติดตามแก้ไข

2. **วิธีดำเนินการ:** ทำอะไรบ้าง ตามลำดับ?
3. **หลักฐาน:** อ้างอิงชุดข้อมูล/วันที่/กติกาใด?
4. **สิ่งที่พบ:** ผลสำเร็จ ข้อยกเว้น ความคลาดเคลื่อน?
5. **บทเรียน:** อะไรควรทำซ้ำ อะไรควรเลิกทำ?
6. **งานค้าง:** ใครต้องทำอะไรต่อ และตรวจผลเมื่อใด?

# ส่วนที่ 4 — ข้อผิดพลาดที่พบบ่อย

| ความผิดพลาด | ผลเสีย | วิธีป้องกัน |
|---|---|---|
| เริ่มจากเลือกกราฟ | กราฟสวยแต่ตอบโจทย์ไม่ได้ | เริ่มจาก Decision Map |
| ไม่กำหนดตัวหาร | เปอร์เซ็นต์ผิดความหมาย | เขียน KPI Dictionary |
| รวมเครื่องเฉพาะภารกิจกับ Workstation | ขอบเขตผิด | นิยาม inclusion/exclusion |
| พบชื่อแล้วสรุปว่าออนไลน์ | ประเมินความพร้อมสูงเกินจริง | แยก enrollment / online / asset proof |
| ซ่อนรายการผิดปกติ | ผู้บริหารไม่เห็นงานที่ต้องแก้ | Exception Register |
| ไม่มีวันอ้างอิง | ผู้อ่านคิดว่าเป็นข้อมูลสด | ติด snapshot timestamp |
| ซ่อนแท็บแล้วคิดว่าปลอดภัย | เปิดเผยข้อมูลทั้งไฟล์โดยไม่ตั้งใจ | แยกไฟล์เผยแพร่และกำหนด Viewer |

# ส่วนที่ 5 — เกณฑ์ว่าเมื่อใด “พอแล้ว”

หยุดเพิ่มฟังก์ชันเมื่อ Dashboard **ตอบคำถามสำคัญได้**, **ข้อมูลตรวจสอบย้อนกลับได้**, **แสดงข้อยกเว้นได้**, **ผู้รับผิดชอบรู้ว่าต้องทำอะไรต่อ**, และ **ภาระดูแลเหมาะกับทรัพยากร**. การหยุดพัฒนาไม่ใช่หยุดปรับปรุง: หากโจทย์หรือความเสี่ยงเปลี่ยน ให้กลับไปทบทวนขั้นที่เกี่ยวข้อง ไม่ใช่เพิ่มกราฟโดยอัตโนมัติ

## สรุป

**Problem → Decision → Scope → Sources → Definitions → Quality → Reconciliation → Governance → Design → MVM → Validation → KM**

**Build • Test • Measure • Prove.**
